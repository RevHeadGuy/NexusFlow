# NexusFlow Implementation Plan

## Status

This repository has a local full-stack prototype: project CRUD, an editable structured brief, persisted workflow templates and decisions, a combined review inbox, stage-specific approval gates, revision-version enforcement, a multi-agent stage-generation pipeline (idea analysis, market research, technical feasibility, PRD, architecture, quality evaluation) with a shared provider abstraction and orchestration lifecycle, an in-process project tool layer shared with the MCP server, an in-project agent-to-agent message bus, reviewable drafts, user-curated research sources, resolvable artifact comments, richer exports, deterministic evaluations, project accounts and roles, shareable invitations, and a read-only MCP server. This plan distinguishes those working foundations from integrations that are still needed for production use.

## Goals

- Deliver a production-oriented multi-agent engineering platform for turning raw ideas into researched, validated project specifications.
- Keep the system modular and auditable.
- Validate each milestone with real tests before moving to the next phase.

## Architecture Summary

### Frontend
- Next.js App Router
- TypeScript, Tailwind CSS, shadcn/ui, Lucide icons
- Dashboard, project workspace, workflow, document viewer, approval controls

### Backend
- FastAPI + Pydantic v2
- SQLAlchemy 2 + SQLite for the documented local setup
- A pipeline of specialized agents (idea analysis, market research, technical feasibility, PRD, architecture, quality evaluation) sharing a `BaseAgent` and an LLM provider abstraction with mock, Groq, and Amazon Bedrock options
- An orchestrator that runs each agent through one lifecycle (run tracking, guardrails, tool reads, A2A handoff, tracing)
- Modular services for projects, workflow, artifacts, evaluations, approval logic, and the A2A message bus

### Supporting Services
- Redis optional for caching/job coordination
- Docker Compose for local stack
- OpenTelemetry-compatible tracing and structured logging

## Phase roadmap

### Foundation (implemented for local development)
- Repository and documentation alignment
- Backend configuration and environment handling
- Health endpoint and startup readiness
- Database session management and basic project CRUD
- Initial backend tests covering health and project creation/retrieval

Acceptance criteria:
- Health endpoint responds successfully
- Project create/list/get endpoints function
- Data persists in a local transactional session
- Tests pass without depending on live LLM access

### Idea discovery (implemented with a provider boundary)
- Idea Analyst agent implementation on the shared `BaseAgent`
- Structured brief schema and persistence
- Real model provider integration with fail-safe configuration
- Frontend project idea form and response display

### Multi-agent pipeline (implemented)
- Shared LLM provider abstraction (`app/agents/providers.py`) covering mock, Groq, and Bedrock, with lenient JSON coercion for live providers
- `BaseAgent` resolving the active prompt (from the prompt registry, with a per-agent default) and returning schema-validated structured output
- Specialized agents for market research, technical feasibility, PRD, architecture, and quality evaluation, each matching the guardrail schema registry
- Orchestrator (`app/services/orchestrator_service.py`) running every agent through start-run → guardrails → persist → tools → A2A handoff → trace, and blocking persistence on HIGH/CRITICAL guardrail violations
- In-process project tool layer (`app/agents/tools.py`) shared with the MCP server; later agents read prior artifacts (e.g. the architecture agent reads the PRD and feasibility artifacts) to ground their output
- In-project A2A message bus (`app/services/agent_message_service.py`) with the default `market_research → technical_feasibility → architecture_agent` handoff chain
- On the mock provider, agent-backed stages fall back to transparent deterministic templates

### Workflow and deliverables (prototype implemented)
- Persisted stage transitions and human decisions
- Reusable workflow profiles with a per-project selectable stage sequence
- Versioned Markdown deliverables for research planning, feasibility, PRD, architecture, quality review, and final package guide, generated by agents with a live provider and by templates on mock
- Research drafts include participant-entered citations; automated source discovery and verification are future work

### Artifacts (partially implemented)
- Markdown artifact viewer and editor; reviewer edits create durable versions
- Version-linked feedback threads with suggested edits and explicit resolution before approval
- Version history and export generation
- ZIP package includes the brief, workflow history, source log, feedback state, and artifact versions

### Project context and review (local, user-curated)
- Edit and persist brief fields; an existing Idea Brief artifact is updated as a new version
- Add source URLs and findings, mark sources as reviewed by a participant, and refresh the Research Plan from the saved log
- Email/password accounts, project owner/editor/reviewer/viewer roles, and single-use invitation links are implemented
- API checks membership and role before project operations; first account claims unowned projects in a legacy local database
- Account verification, password recovery, login rate limiting, email delivery, organization management, and production session revocation are future work
- Workflow approvals require the stage's deliverables, clean content checks, no unresolved blocking findings or comments, and revised versions after a change request
- Review inbox combines active workflow stage reviews with standalone HITL checkpoints

### Reliability (partially implemented)
- Devil's Advocate, consistency check, deterministic evaluation engine
- A complementary model-based Quality Evaluator agent when a live provider is configured
- Deterministic validation and test datasets

### MCP tooling and tool layer (local, read-only implementation)
- Shared read-only tool layer (`app/agents/tools.py`) used in-process by agents and wrapped over Streamable HTTP by the MCP server — one implementation, two entry points
- Streamable HTTP MCP endpoint for project context and artifacts
- Access to multi-member projects is disabled until the MCP transport can enforce per-user membership; the in-process agent path has no such limit because it runs inside the authenticated request
- Mutating tools and external MCP server connections are not enabled

### Agent-to-agent messaging (implemented, in-process)
- Persisted `agent_messages` bus scoped to a single project, with send/consume and a readable log at `GET /projects/{id}/agent-messages`
- Default handoff chain `market_research → technical_feasibility → architecture_agent`, recorded as project traces
- Internal and in-process only; cross-service or cross-network handoff remains future work

### Frontend delivery (separate from backend roadmap)
- Next.js app shell, first-run sample project, and dashboard UI
- Workflow stage, decision history, and artifact versions persist and can be resumed from the project workspace
- Project starter templates and workflow stage selection
- CI, deployment docs, and end-to-end verification

## Risk Notes

- Strands SDK interfaces must be validated against the installed package rather than guessed.
- Postgres should be the canonical production store, but local development may fall back to a lightweight SQLite configuration when no database is configured.
- Human approval must be stored explicitly before workflow continuation.

## Implementation Rules

- Preserve and extend useful existing files.
- Avoid fake/mock-only flows that do not actually persist or validate state.
- Keep modules small, typed, and testable.
- Maintain a clear distinction between implemented, partially implemented, and planned work.
